# SmartRoute — Полный технический и бизнес-брифинг

*Документ для подготовки к переговорам с клиентом. Содержит только проверенные факты из кода системы.*

*Актуально на: июнь 2026*

---

## Что такое SmartRoute

SmartRoute — это веб-сервис для автоматического планирования маршрутов доставки. Диспетчер вводит адреса магазинов, выбирает машины и водителей — система за несколько секунд строит оптимальные маршруты, отправляет их водителям прямо в Яндекс Навигатор и WhatsApp.

**Основная проблема, которую решает система:** в большинстве компаний доставки маршруты строятся «на глаз» или по привычке. Водитель едет так, как ему удобно. Это приводит к лишним километрам, перерасходу топлива, опозданиям и хаосу при любом изменении в расписании.

## Полный список функций (что реально работает)

### 1. База магазинов (точек доставки)

- Хранение базы всех торговых точек в PostgreSQL
- Создание, редактирование, удаление точек
- **Геокодинг**: адрес → координаты через Яндекс Геокодер (первичный) или Nominatim/OpenStreetMap (резервный, бесплатный)
- Поддержка ссылок из Яндекс Карт — вставляешь ссылку, система сама извлекает координаты
- **Импорт из Excel** — загрузка до сотен точек одним файлом (формат: название, адрес, город, телефон, часы работы, временные окна, ссылка на карту)
- Скачивание шаблона Excel прямо из системы
- Отображение всех точек на интерактивной карте (тайлы 2ГИС — без политически спорного контента)
- Просмотр каждой точки в Яндекс Картах одной кнопкой
- Фильтрация точек по городу

### 2. Планирование маршрутов

- Настройка склада (депо): адрес или ссылка Яндекс Карт, сохраняется между сессиями
- Выбор числа машин (1–50)
- Настройка каждой машины: название, имя водителя
- Сохранение автопарка как шаблон — не нужно вводить каждый раз
- **Временны́е окна доставки**: можно указать, в какое время принимает каждый магазин (например, 10:00–14:00), и система это учтёт при построении маршрута
- Время разгрузки на каждой точке (учитывается при расчёте расписания)
- Выбор конкретных магазинов из базы или всех сразу
- Предупреждение при выборе точек без координат

### 3. Алгоритм оптимизации (VRP-решатель)

Это ядро системы. Используется **Google OR-Tools** — профессиональный решатель задачи маршрутизации транспорта (VRP, Vehicle Routing Problem), который применяется в логистике мирового уровня.

**Как работает алгоритм (6 шагов):**

1. **Кластеризация методом развёртки (Sweep)**: магазины разбиваются на сектора по географическому углу от склада. Каждый кластер — отдельный маршрут. Затем 3 итерации уточнения по ближайшему центроиду — граничные точки переходят в геометрически оптимальный кластер.

2. **Матрица расстояний по реальным дорогам**: для каждого кластера система запрашивает OSRM (Open Source Routing Machine на базе OpenStreetMap) — это реальные дороги, не "по прямой". Бесплатно, без API-ключа, до 100 точек на кластер. Параллельно по всем кластерам.

3. **OR-Tools TSP на каждый кластер**: Google OR-Tools решает задачу коммивояжёра (оптимальный порядок объезда) с учётом временных окон. Адаптивный бюджет времени: до 5 точек — 0.3 сек, до 10 точек — 1.0 сек, больше — 2.0 сек на кластер.

4. **Заполнение пустых машин**: если из-за географии какой-то маршрут остался пустым — самый большой маршрут делится пополам.

5. **Межмаршрутная оптимизация Or-opt**: после решения TSP по каждому кластеру система проверяет, выгодно ли перенести точку из одного маршрута в другой. До 5 итераций, до 80 точек. Именно этот шаг даёт **дополнительные −15–40% километров** по сравнению с простым TSP.

6. **Балансировка минимума точек**: гарантирует, что у каждого водителя не менее 5 точек (или пропорционально меньше, если точек объективно мало). Если Or-opt «обнулил» какой-то маршрут — ребалансер забирает ближайшую точку у перегруженного водителя с минимальным штрафом по дистанции.

**Почему это лучше, чем "на глаз"?**

Человек при виде 30 точек на карте инстинктивно строит маршрут по привычке или по визуальной очевидности. Задача коммивояжёра для N точек имеет (N-1)!/2 вариантов — для 20 точек это 60 квинтиллионов комбинаций. Мозг физически не может перебрать даже малую часть. OR-Tools использует метаэвристику (guided local search) и обходит пространство решений за секунды, находя решение, близкое к глобальному оптимуму.

### 4. Результаты и навигация

- Интерактивная карта с маршрутами всех машин (цветная легенда)
- Детализация по каждой машине: список точек с адресами, временем прибытия, порядком объезда
- **Ссылки Яндекс Навигатора** — одна кнопка, водитель открывает готовый маршрут в приложении
- Склад включён в ссылку как стартовая точка — Яндекс Навигатор заменяет её GPS-позицией водителя, все магазины сохраняются
- Автоматическое разбиение маршрутов > 19 магазинов на сегменты (ограничение Яндекс Навигатора — не более 20 точек в одной ссылке: склад + 19 магазинов). Водитель получает несколько ссылок — проезжает по очереди.
- Кнопка копирования ссылки для каждого водителя
- **Отправка в WhatsApp**: система формирует текстовое сообщение с именем водителя, списком магазинов, общим километражем и ссылкой на маршрут. Диспетчер нажимает кнопку — открывается WhatsApp с готовым текстом.
- Мобильный режим для водителя (просмотр своего маршрута с телефона)

### 5. История маршрутов

- Все построенные маршруты сохраняются в базе данных
- Таблица сессий: дата, число машин, число точек, пробег, экономия
- Переход к любому историческому маршруту — можно показать водителю или повторить

### 6. Аналитика

- Выбор периода: 30 дней, 90 дней, 6 месяцев, 1 год, произвольный диапазон с выбором дат
- **График пробега по дням** — видно, когда было больше доставок
- **График экономии по месяцам** — в рублях, накопительно
- **Загрузка машин** — сколько точек в день приходилось на каждое авто
- **Топ-10 магазинов** по частоте доставок — понятно, кто самый активный клиент
- Сводные метрики: общий пробег за период, суммарная экономия, среднее число точек в день

## Как считается экономия (точные формулы из кода)

Это важно понимать, чтобы говорить клиенту честные цифры.

### Базовый маршрут (с чем сравниваем)

Система строит **"наивный" маршрут** — каждый водитель объезжает свои точки в порядке случайного назначения (не оптимизированном). Расстояния считаются **по прямой (Haversine)** — одинаково для обоих вариантов.

### Оптимизированный маршрут

Тот, который построил OR-Tools, тоже измеряется по Haversine.

### Почему Haversine на обеих сторонах — это честно

Система применяет одну и ту же метрику (расстояние по прямой) к наивному и оптимизированному маршруту. Соотношение остаётся верным независимо от метрики. Если оптимальный порядок объезда короче наивного на 20% по прямой — он будет короче примерно на те же 20% по реальным дорогам.

### Формулы экономии

```
saved_km = unoptimized_km − optimized_km        (по Haversine)
saved_pct = saved_km / unoptimized_km × 100

ROAD_FACTOR = 1.4   (коэффициент: реальный пробег / Haversine)
saved_km_road = saved_km × 1.4   (реальный сэкономленный пробег)

cost_per_km = 31 руб/км (реальных дорог)
  → топливо:      7 руб/км  (Газель, дизель 10 л/100км × 70 руб/л)
  → водитель+СВ: 13 руб/км
  → ТО:           7 руб/км
  → накладные:    4 руб/км

saved_rub_day = saved_km_road × 31 руб/км
saved_rub_month = saved_rub_day × 30
```

### Пример реальных цифр

10 машин, 80 точек, маршрут по Махачкале:
- Наивный пробег: ~420 км
- Оптимизированный: ~310 км
- Экономия: 110 км (26%)
- По реальным дорогам (×1.4): ~154 км
- Экономия в день: 154 × 31 = **4 774 руб**
- Экономия в месяц: **~143 000 руб**

*Цифры иллюстративные — реальный результат зависит от географии точек.*

## Что система НЕ делает (честный список проблем и ограничений)

### Критические ограничения для продажи

**1. Нет авторизации и разграничения прав**

Система не имеет логина. Кто знает URL — тот видит всё. Это значит: одну установку системы может использовать только одна компания, доступ защищается только тем, что URL не публичный. Для многопользовательского SaaS (несколько клиентов на одном сервере) нужна доработка.

*Для первого клиента: не проблема. Просто дайте им URL и они одни.*

**2. Нет мобильного приложения водителя**

Водители работают через ссылки в Яндекс Навигаторе и WhatsApp. Собственного приложения нет. Это работает на практике, но не так удобно, как специализированные driver apps.

**3. Учёт нагрузки — только по количеству точек**

Система не учитывает реальный вес или объём товаров — каждая точка считается как 1 единица. Если в одном магазине разгружают 10 паллет, а в другом 1 коробку — система этого не видит. Это упрощение для MVP.

**4. Нет реального трафика**

Время прибытия рассчитывается из средней скорости 30 км/ч. Пробки, ремонт дорог, сезонные условия не учитываются. Яндекс Навигатор при открытии ссылки скорректирует маршрут с учётом пробок — но расчётное время в системе будет примерным.

**5. Ограничение Яндекс Навигатора — 20 точек на ссылку**

Мобильное приложение Яндекс Навигатора не строит маршрут с более чем 20 остановками. Система автоматически разбивает маршрут на сегменты (склад + 19 магазинов = 20 точек) и даёт несколько ссылок. Водитель должен переключиться между ними вручную в нужной точке.

**6. Кэши хранятся в памяти процесса**

Кэш геокодирования, кэш матриц расстояний — хранятся в оперативной памяти сервера. При перезагрузке сервера они сбрасываются. Это не влияет на данные (магазины и маршруты в PostgreSQL), но первые запросы после рестарта будут медленнее.

**7. Геокодирование без Yandex API ключа — медленное**

Если ключ Яндекс Геокодера не установлен, система использует Nominatim (OpenStreetMap) — максимум 1 запрос в секунду. Импорт 200 магазинов займёт 3+ минуты вместо 30 секунд. *С ключом это не проблема.*

**8. VRP — это NP-сложная задача**

Математически гарантировать абсолютный оптимум невозможно. Система находит очень хорошее решение за 2–10 секунд, но не обязательно идеальное. На практике это несущественно — разница между "очень хорошим" и "идеальным" маршрутом — единицы километров.

**9. OSRM — публичный сервер**

По умолчанию расчёт матрицы расстояний идёт через публичный сервер router.project-osrm.org. Это бесплатно и работает хорошо, но зависит от доступности внешнего сервиса. При недоступности OSRM — система автоматически переключается на расчёт "по прямой" (Haversine), что немного снижает точность оптимизации, но не ломает работу.

### Некритические особенности

- Аналитика не строит прогнозы — только исторические данные
- Нет интеграции с 1С, ERP или WMS-системами
- Нет учёта расхода топлива по факту (только расчётные цифры)
- Нет push-уведомлений водителям
- Нет подтверждения доставки водителем

## Для кого эта система (идеальный клиент)

**Подходит:**
- Дистрибьюторы FMCG (продукты, напитки, табак, бытовая химия) — 5–30 машин, 30–200 точек в день
- Оптовые компании с регулярными маршрутами
- Компании с несколькими водителями, где диспетчер планирует маршруты "на глаз" или в Excel
- Бизнесы, где водители сами решают порядок объезда

**Не подходит сейчас:**
- Курьерские службы с разовыми заказами (нужна динамическая диспетчеризация)
- Компании с весовыми ограничениями по машинам (нет учёта веса груза)
- Бизнес с более чем 50 машинами без сопровождения (система не тестировалась на таких объёмах)

## Технические характеристики для технического директора клиента

- **Хранение данных:** PostgreSQL, все данные клиента изолированы на его Railway-проекте
- **Доступность:** Railway Pro гарантирует 99.99% uptime
- **Время построения маршрута:** 3–15 секунд для 5–100 точек
- **Безопасность данных:** HTTPS, данные на сервере клиента, API-ключи в переменных окружения
- **Масштаб:** протестировано на 100 точках, 20 машинах. Теоретический лимит OR-Tools — тысячи точек
- **Интерфейс:** работает в любом браузере, включая мобильный — отдельное приложение не нужно
- **Резервное копирование:** Railway делает автоматические бэкапы PostgreSQL
- **Минимум точек на водителя:** не менее 5 (или пропорционально если точек мало) — маршруты всегда операционно осмысленны
