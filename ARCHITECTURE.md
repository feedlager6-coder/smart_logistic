## Что такое SmartRoute?

SmartRoute — это веб-приложение для дистрибьюторов, которое автоматически строит оптимальные маршруты доставки для нескольких машин. Диспетчер загружает список магазинов (вручную или через Excel), указывает машины, нажимает кнопку — и получает готовые маршруты на карте с ссылками на Яндекс Навигатор.

## Где OR-Tools (алгоритм оптимизации)

**Файл:** `artifacts/api-server/main.py`, функция `solve_vrp()`

**OR-Tools** — это библиотека от Google для решения задачи VRP (Vehicle Routing Problem — задача маршрутизации транспортных средств).

### Цель оптимизации (с 31.05.2026)

**Главная цель**: минимальный общий пробег и время доставки.  
**НЕ цель**: равномерное распределение точек по водителям.

Если одному водителю выгодно дать 12 точек, а другому 5 — система так и сделает.

### Алгоритм `solve_vrp()` (4 шага)

```
Шаг 1: Haversine NxN матрица (всегда — гарантированный fallback)
  → Мгновенно, без API, работает без ключей

Шаг 2: Равно-угловая секторная разбивка + centroid refinement (Этап A)
  → 360° вокруг депо делятся на N равных угловых "клиньев"
  → Плотный клин → больше точек; разреженный → меньше
  → 3 итерации centroid refinement — точки у границ секторов
    переназначаются к ближайшему геометрическому центроиду
  → Нет round-robin; нет SetGlobalSpanCostCoefficient

Шаг 3: Дорожная матрица per-cluster + OR-Tools TSP/TSPTW (Этапы B + C)
  → Приоритетная цепочка для каждого кластера:
  →   1) GraphHopper (платный, точные данные ОСМ + пробки)
  →   2) OSRM (бесплатный, реальные дороги OSM, без API-ключа, до 100 точек)
  →   3) Haversine (прямая линия, всегда доступен, мгновенно)
  → OR-Tools TSP (или TSPTW при use_time_windows=true):
  →   – Адаптивный таймаут: ≤5 остановок → 0.3 с; ≤10 → 1.0 с; >10 → 2 с
  →   – При time_windows: OR-Tools Time Dimension, отправка 09:00,
  →     принудительные окна прибытия, slack 60 мин

Шаг 4: Заполнение пустых машин
  → Если угловой клин пуст → крупнейший маршрут делится пополам
  → Все машины всегда получают работу
```

### Цепочка дорожных матриц (GH → OSRM → Haversine)

Три слоя, проверяются по порядку для каждого кластера независимо:

#### GraphHopper — `get_cluster_matrix_gh()`

| Возможность | Описание |
|---|---|
| Требует | `GRAPHHOPPER_API_KEY` |
| In-memory кэш | `_matrix_cache[(lat,lon)...]` — повторные вызовы = 0 API запросов |
| Авто-калибровка | 400 "Too many points, allowed: N" → `_gh_plan_limit = N` автоматически |
| Счётчики | `_gh_call_successes`, `_matrix_cache_hits`, `_matrix_cache_misses` |
| Graceful fallback | Любая ошибка → None → следующий слой (OSRM) |

#### OSRM — `get_cluster_matrix_osrm()`

| Возможность | Описание |
|---|---|
| Требует | Ничего — публичный сервер без ключа |
| Сервер по умолчанию | `router.project-osrm.org` (fair use, до 100 точек/запрос) |
| Self-hosted | `OSRM_BASE_URL` env-var для собственного сервера |
| Данные | OpenStreetMap — реальные дороги, односторонние улицы, мосты |
| Кэш | Тот же `_matrix_cache` с префиксом `("osrm",)` |
| Счётчики | `_osrm_call_successes`, `_osrm_cache_hits` |
| Координаты | **lon, lat** порядок в URL (OSRM-специфика!) |
| Graceful fallback | Любая ошибка/таймаут → None → Haversine |

#### Haversine — всегда доступен

Прямолинейное расстояние по формуле Haversine. Без API, без сети, мгновенно.
Используется для кластеров, которые не вошли в GH и OSRM.

**Переменные конфигурации**:
- `GRAPHHOPPER_API_KEY` — ключ GH API
- `GRAPHHOPPER_CLUSTER_MAX` — максимальный размер кластера для GH (default 25)
- `OSRM_BASE_URL` — URL OSRM сервера (default: публичный router.project-osrm.org)
- `OSRM_MAX_LOCATIONS` — лимит точек на кластер для OSRM (default 100)
- `ORTOOLS_TIME_LIMIT_SECONDS` — максимальный лимит OR-Tools TSP per кластер (default 2, float);
  адаптивно снижается для малых кластеров: ≤5 → 0.3 с; ≤10 → 1.0 с
- `CLUSTER_CENTROID_REFINEMENT_ROUNDS` — итерации centroid refinement (default 3)

## Где геокодирование (адрес → координаты)

**Файл:** `artifacts/api-server/main.py`, функция `geocode_address()` (строки 157–178)

Используется **Nominatim** — бесплатный сервис геокодирования от OpenStreetMap.

Как работает:
1. Получает текстовый адрес: `"Москва, ул. Ленина, 5"`
2. Делает запрос к Nominatim API
3. Получает координаты: `(55.7558, 37.6173)`
4. Кэширует результат в памяти (не запрашивает повторно)
5. При импорте из Excel — делает паузу 1.1 секунды между запросами (ограничение Nominatim: не более 1 запроса в секунду)

## Где оптимизация маршрутов

Цепочка обработки при нажатии кнопки "Построить маршрут":

1. **Фронтенд** (`pages/route.tsx`) — пользователь выбирает магазины и машины, отправляет запрос
2. **Бэкенд** (`/api/route/build` в `main.py`) — получает запрос, загружает координаты магазинов из базы
3. **`solve_vrp()`** — OR-Tools строит оптимальные маршруты
4. **`calculate_savings()`** — считает экономию
5. **Ответ** содержит маршруты, ссылки на Яндекс и WhatsApp
6. **Фронтенд** (`pages/result.tsx`) — показывает карту Leaflet с маршрутами

## Ограничение Яндекс.Навигатора и механизм автоматической разбивки маршрутов

### Проблема

Яндекс.Навигатор (мобильное приложение) поддерживает не более **20 промежуточных точек** в одном `rtext`-URL формата:

```
https://yandex.ru/maps/?rtext=lat1,lon1~lat2,lon2~...~latN,lonN&rtt=auto
```

При превышении лимита приложение перестаёт строить маршрут. Веб-версия работает с большим числом точек, но мобильный навигатор — основной инструмент водителей.

### Решение

Константа `YANDEX_NAV_MAX_STOPS = 20` в `artifacts/api-server/main.py`.

Функция `yandex_nav_urls(coords_list: list) -> list[str]` разбивает список координат на чанки по 20 и возвращает отдельную URL для каждого сегмента.

**Пример: водитель с 27 точками получает 2 ссылки:**
- Часть 1 (остановки 1–20): `https://yandex.ru/maps/?rtext=...&rtt=auto` (20 точек)
- Часть 2 (остановки 21–27): `https://yandex.ru/maps/?rtext=...&rtt=auto` (7 точек)

### Таблица сегментации

| Точек в маршруте | Сегментов | Распределение |
|---|---|---|
| 1–20 | 1 | все точки в одной ссылке |
| 21–40 | 2 | 20 + остаток |
| 41–60 | 3 | 20 + 20 + остаток |
| N | ⌈N/20⌉ | равномерно по 20 |

### API-поля

- `yandex_urls: string[]` — список всех сегментов (новое поле)
- `yandex_url: string` — первый сегмент, для обратной совместимости

### UI (result.tsx)

- Если `yandex_urls.length > 1` → показывается amber-предупреждение
- Для каждого сегмента — отдельная строка «Часть N (ост. X–Y)» с кнопками «Открыть» и «Скопировать»
- Маршруты ≤20 точек — UI не изменился

### Что НЕ меняется при разбивке

Разбивка касается только навигационных ссылок. Всё остальное остаётся без изменений:
- `total_km` — суммарный пробег
- `saved_km`, `saved_pct`, `saved_fuel_l`, `saved_fuel_cost_rub`, `saved_rub_day` — экономия
- Порядок точек в маршруте
- Карта Leaflet
- WhatsApp-ссылка

## Модель расчёта экономии (calculate_savings)

**Аудит проведён 03.06.2026.** Результат: текущая модель корректна.

### Принцип

Сравниваются два маршрута, оба через **Haversine** (прямолинейное расстояние):

| Маршрут | Метод | Описание |
|---------|-------|---------|
| Baseline (unoptimized) | Haversine | Round-robin в порядке ввода — «как диспетчер без оптимизации» |
| Optimized | Haversine | Реальный маршрут после solve_vrp() |

Использование Haversine на обеих сторонах — это не ошибка, это **консистентное сравнение**.
OSRM используется только для нахождения оптимального **порядка** посещений (внутри solve_vrp),
но не для отчётных расстояний.

### Монетарные расчёты

Для денег и топлива применяется `ROAD_FACTOR = 1.4`:

```
saved_km_road = saved_km × 1.4          # Haversine → реальный пробег
saved_fuel_l  = saved_km_road × 0.1     # 10 л/100 км
saved_rub_day = saved_km_road × 31      # 31 руб/км (разбивка ниже)
```

`cost_per_km = 31 руб/км` — задокументированная разбивка для Газели 2026:
- Топливо: 7 руб/км (10 л × 70 руб/л / 100 км)
- Водитель (с СВ): 13 руб/км (65 000 руб/мес / 25 дн / 200 км)
- ТО + износ: 7 руб/км
- Накладные/страховка: 4 руб/км

### Почему не OSRM для отчётности

Проведён аудит 10 сценариев (Махачкала + Москва). Результат:
- Δsaved_pct = −6.4% (ниже порога 15% для обоснованного перехода)
- OSRM публичный сервер даёт аномальные результаты для Махачкалы в 30% случаев (road_factor 32–117×)
- ROAD_FACTOR=1.4 аппроксимирует OSRM с точностью ±10% (avg OSRM km_ratio = 1.308)

**Вывод:** Haversine + ROAD_FACTOR надёжнее и точнее для производственного использования.

## Деплой на Railway

SmartRoute деплоится как **один Railway-сервис** (backend + frontend в одном контейнере).

```
┌─────────────────────────────────────────┐
│  Railway Service                        │
│                                         │
│  Docker Stage 1: Node.js 20            │
│    pnpm install → vite build           │
│    → dist/public/ (React bundle)       │
│                                         │
│  Docker Stage 2: Python 3.11-slim      │
│    pip install requirements.txt        │
│    COPY main.py                        │
│    COPY dist/public/ → ./static/       │
│                                         │
│  Runtime (FastAPI):                    │
│    /api/*    → API handlers            │
│    /assets/* → JS/CSS bundles          │
│    /*        → index.html (SPA)        │
└───────────────┬─────────────────────────┘
                │ DATABASE_URL (auto)
┌───────────────▼─────────────────────────┐
│  Railway PostgreSQL Plugin              │
│  (автоматически инжектирует DATABASE_URL│
└─────────────────────────────────────────┘
```

**Почему single-service?** Vite-proxy (`/api → localhost:8080`) работает только в dev.
В production frontend делает запросы к тому же origin → FastAPI должен отвечать на
`/api/*` и отдавать `index.html` на все остальные пути.

**DB-миграции**: `init_db()` использует `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE … ADD COLUMN IF NOT EXISTS`.
Запускается при каждом старте, идемпотентна. Ручное применение миграций не нужно.

Подробная инструкция: `DEPLOY.md`

---

## Ключевые зависимости

### Python (бэкенд)
| Пакет | Зачем |
|---|---|
| `fastapi` | Веб-фреймворк для API |
| `uvicorn[standard]` | Сервер для запуска FastAPI |
| `ortools` | Алгоритм оптимизации маршрутов (Google OR-Tools) |
| `psycopg2-binary` | Подключение к PostgreSQL |
| `openpyxl` | Чтение и создание Excel-файлов |
| `python-multipart` | Загрузка файлов через форму |
| `aiofiles` | Асинхронное обслуживание статических файлов (FileResponse) |
| `pydantic` | Валидация входящих данных |

### JavaScript / TypeScript (фронтенд)
| Пакет | Зачем |
|---|---|
| `react` | Библиотека для построения интерфейса |
| `vite` | Инструмент сборки |
| `wouter` | Роутер (переключение страниц) |
| `@tanstack/react-query` | Кэширование и управление запросами к API |
| `leaflet` + `react-leaflet` | Интерактивная карта |
| `recharts` | Графики и диаграммы |
| `tailwindcss` | CSS-стили |
| `shadcn/ui` | Готовые UI-компоненты (кнопки, таблицы и т.д.) |
| `lucide-react` | Иконки |
| `orval` | Генерация TypeScript-клиента из OpenAPI |
| `zod` | Валидация типов данных |
