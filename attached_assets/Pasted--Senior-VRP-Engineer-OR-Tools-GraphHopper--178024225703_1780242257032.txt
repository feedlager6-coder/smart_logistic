КОНТЕКСТ

В проекте уже присутствует:

* GraphHopper API Key
* Yandex Geocoder API Key
* OR-Tools
* FastAPI backend
* PostgreSQL
* существующая VRP логика

По результатам аудита выяснилось, что OR-Tools сейчас использует Haversine distance matrix.

То есть оптимизация происходит по расстояниям по прямой между координатами.

Это приводит к тому, что алгоритм не знает о:

* реальных дорогах;
* односторонних улицах;
* мостах;
* тупиках;
* объездах;
* дорожной сети.

ЦЕЛЬ

Перевести VRP-оптимизацию на реальные дорожные расстояния и время движения через GraphHopper Matrix API.

ТРЕБОВАНИЯ

1. Изучи текущий solve_vrp() и все связанные функции.
2. Найди место, где создается Haversine distance matrix.
3. Замени ее на GraphHopper Matrix API.
4. Используй существующий GRAPHHOPPER_API_KEY.
5. Реализуй гибридную схему:

Этап A:
Быстрая географическая кластеризация.

Этап B:
Для каждого кластера получать реальную матрицу времени и расстояний через GraphHopper Matrix API.

Этап C:
Передавать эту матрицу в OR-Tools.

6. Добавить кэширование матриц.

Если набор координат уже рассчитывался ранее:

* не обращаться к GraphHopper повторно;
* использовать сохранённый результат.

7. Добавить защиту от лимитов API:

* логирование количества запросов;
* graceful fallback;
* использование существующей Haversine матрицы только если GraphHopper недоступен.

8. Проверить, используются ли в оптимизации:

* delivery window;
* service time;
* unloading time;
* vehicle capacity.

Если поля уже существуют, но не участвуют в расчётах:

показать это в отчёте.

Ничего не внедрять автоматически без подтверждения.

ТЕСТИРОВАНИЕ

Создать тестовые сценарии:

* 30 магазинов / 4 машины
* 50 магазинов / 6 машин
* 100 магазинов / 8 машин

Для каждого сценария показать:

* количество вызовов GraphHopper;
* время расчёта;
* общий пробег;
* общее время;
* сравнение с предыдущей реализацией.
