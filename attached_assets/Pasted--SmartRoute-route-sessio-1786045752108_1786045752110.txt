Ознакомься с архитектурой проекта SmartRoute и текущей реализацией исполнения доставок (route_session / route_assignments / route_executions).

Нужно исправить и довести MVP исполнения доставок до логически правильного состояния. Не внедряй GPS, live-карту, WebSocket и новые сложные сущности.

Контекст:
- Проект должен работать не только для воды, но и для продуктов, мебели и B2B-доставок.
- Водитель открывает защищённую ссылку без логина.
- Диспетчер видит исполнение по каждой машине.

Исправить следующее:

1. Частичная доставка (КРИТИЧНО)
Сейчас при:
- план = 2
- статус = partial
- actual_qty = 1
сервер возвращает HTTP 422.

Нужно исправить валидацию и/или передачу actual_qty, чтобы сценарий 1 из 2 работал корректно.

2. Отображение количества
В панели диспетчера и у водителя показывать:
- План: 2
- Доставлено: 1
- Остаток: 1

Формат должен быть понятным одним взглядом.

3. Остаток после partial
После частичной доставки диспетчер должен видеть кнопку:
«Создать заявку на остаток».

Новая заявка должна создаваться только на недоставленное количество.

4. Не доставлено
Для статуса failed:
- actual_qty = 0
- диспетчер должен видеть кнопку «Создать заявку на новую дату».

5. Перенесено
Текущая логика переноса работает — её не ломать.
Но убедиться, что переносится весь недоставленный объём.

6. Кнопки оплаты
У водителя заменить select на крупные кнопки:
Способ оплаты:
- Наличные
- Карта
- Перевод

Статус оплаты:
- Оплачено
- Не оплачено

7. WhatsApp
При отправке маршрута в WhatsApp добавить вторую ссылку:
- ссылка на навигацию/маршрут
- ссылка на исполнение доставок (/driver/{token})

8. UI водителя
Сделать сценарий максимально быстрым:
- выбрать действие (4 большие кнопки)
- при partial показать поле количества
- при failed/rescheduled скрыть поле количества
- при rescheduled показать поле причины

9. Проверить polling
Комментарий, количество и оплата должны появляться у диспетчера без перезагрузки страницы.

Важно:
- Не переписывай архитектуру.
- Не добавляй GPS и ETA.
- Не меняй логику маршрутизации.
- Сначала найди причину 422, затем внеси минимальные исправления.
- После изменений протестируй 4 сценария:
  1) delivered 2/2
  2) partial 1/2
  3) failed 0/2
  4) rescheduled 0/2 + новая дата.

В конце дай короткий отчёт: что исправлено, что осталось и есть ли риски для существующих маршрутов.
