SMARTROUTE — ФИНАЛЬНОЕ РАССЛЕДОВАНИЕ И АУДИТ АЛГОРИТМА

Контекст проекта

Это логистическая система SmartRoute.

Стек:

	•	Backend: FastAPI
	•	PostgreSQL (Railway)
	•	OR-Tools
	•	OSRM / GraphHopper
	•	React Frontend

У тебя есть полный доступ к репозиторию.

Перед любыми изменениями ОБЯЗАТЕЛЬНО:

	1.	Изучи весь проект.
	2.	Изучи архитектуру маршрутизации от начала до конца.
	3.	Изучи solve_vrp, кластеризацию, OR-Tools, 2-opt, inter_route_relocate, ETA.
	4.	Изучи структуру БД.
	5.	Изучи реальные данные Railway.
	6.	Изучи историю изменений в коде.
	7.	Только после полного понимания системы переходи к выводам.

Запрещено:

	•	Вносить изменения до завершения расследования.
	•	Делать предположения без проверки.
	•	Удалять существующие улучшения без доказательства.
	•	Ломать рабочий API.

Реальный кейс

В базе есть реальная сессия:

	•	120 магазинов
	•	9 автомобилей

Факт:

Один маршрут получил 37 точек.

Среднее:
120 / 9 ≈ 13.3 точки

Максимальный маршрут:
37 точек

Пользователь сравнил маршрут SmartRoute и тот же маршрут после нажатия кнопки “Оптимизировать маршрут” в Яндекс Картах.

Результат:

SmartRoute:
1 час 57 минут

Яндекс:
1 час 43 минуты

Разница:
14 минут

Что нужно расследовать

Часть 1. Проверка текущих улучшений

Проверить:

	•	работает ли повторный 2-opt после relocate;
	•	работает ли снятие лимита <=80;
	•	реально ли помогают новые лимиты OR-Tools;
	•	есть ли регрессии после изменений;
	•	насколько улучшение подтверждается цифрами.

Часть 2. Главный вопрос

Почему при среднем 13 точек один водитель получает 37 точек?

Нужно доказательно определить:

	•	это баг;
	•	это следствие географии;
	•	это следствие sweep-кластеризации;
	•	это следствие расположения депо;
	•	это следствие relocate.

Нужны реальные цифры из БД.

Часть 3. Ограничение Яндекса

Важный факт:

Яндекс автоматически делит маршруты при количестве точек более 20.

Проверить:

Если принудительно ограничить маршрут максимумом 20 точками:

	•	что произойдёт с общим пробегом;
	•	что произойдёт со временем;
	•	что произойдёт с балансом нагрузки;
	•	станет ли маршрут лучше.

Ничего не внедрять.

Сначала провести моделирование.

Часть 4. Сравнение с Яндексом

Пользователь уже предоставил:

	•	маршрут SmartRoute;
	•	маршрут после оптимизации Яндексом.

Нужно:

	1.	Сравнить порядок посещения.
	2.	Найти конкретные отличия.
	3.	Найти точки, где Яндекс выигрывает.
	4.	Найти точки, где SmartRoute выигрывает.
	5.	Определить источник выигрыша Яндекса:

	•	другой порядок;
	•	более сильный локальный поиск;
	•	дорожные ограничения;
	•	пробки;
	•	распределение точек;
	•	другое.

Запрещено делать выводы без цифр.

Часть 5. Реальные данные БД

Обязательно использовать реальные данные Railway.

Проверить:

	•	stores
	•	route_sessions
	•	route_session_stores
	•	company_settings

Особенно интересуют:

	•	последние сессии;
	•	сессия с 120 магазинами и 9 машинами;
	•	история построений с теми же магазинами.

Часть 6. Стресс-тесты

После расследования провести стресс-тесты.

Минимум:

	•	50 точек
	•	100 точек
	•	120 точек
	•	150 точек
	•	200 точек
	•	300 точек

Для каждого сценария показать:

	•	время расчёта;
	•	общий километраж;
	•	максимальный маршрут;
	•	минимальный маршрут;
	•	количество точек по машинам;
	•	ratio max/min;
	•	среднее количество точек.

Часть 7. Финальный отчёт

В конце нужен один отчёт.

Структура:

	1.	Подтверждённые проблемы.
	2.	Опровергнутые гипотезы.
	3.	Узкие места алгоритма.
	4.	Что реально даёт выигрыш.
	5.	Что НЕ стоит менять.
	6.	Какие изменения внедрять.
	7.	Какие изменения НЕ внедрять.
	8.	Оценка эффекта каждого изменения в процентах и километрах.

Важно:

Не писать код до завершения расследования.

Сначала полный аудит.

Только после получения отчёта будет принято решение о внедрении изменений.
