Ознакомься с архитектурой SmartRoad и текущей реализацией route_session / route_assignments / route_executions.

Важно: сейчас проект должен остаться рабочим. Нельзя делать рефакторинг, миграции, новые таблицы, новые поля БД, plan_qty, CI/CD, тестовое окружение, bcrypt, login, WebSocket, GPS или ETA.

Нужно только ОКОНЧАТЕЛЬНО исправить логику количества товаров и частичной доставки.

Контекст:
- Водитель открывает защищённую ссылку.
- Есть большие кнопки: Доставлено / Частично / Не доставлено / Перенесено.
- Перенос заявки уже работает правильно.
- Деплой Railway должен остаться зелёным.

Текущий баг:
- Для части точек отображается «План: 0», хотя в поле Груз указано, например, «2 воды».
- Из-за этого статус «Частично» даёт HTTP 422.

Сначала проанализируй, где именно quantity становится 0.
Не меняй архитектуру.

ТРЕБОВАНИЯ

1. quantity остаётся единственным плановым количеством.

2. При создании route_execution:
   - если stop.quantity > 0 → использовать его;
   - иначе попытаться извлечь количество из поля products.

3. Поддержать форматы:
   - 2 воды
   - 1 вода
   - воды 3
   - вода x2
   - 2 бутыли
   - бутыль 1
   - Молоко x5

4. Если количество определить нельзя → quantity = 1.

5. Никогда не создавать execution с quantity=0.

6. Для уже существующих execution с quantity=0:
   - при открытии /api/driver/{token}
   автоматически восстановить quantity из products (только в памяти или через безопасочный update без миграций).

7. Исправить partial:
   - quantity=2
   - actual_qty=1
   - status=partial
   должно сохраняться без 422.

8. Для partial:
   - диспетчер должен видеть:
     План 2 • Доставлено 1 • Остаток 1.
   - должна работать кнопка «Создать заявку на остаток».

9. Для failed:
   - должна работать кнопка «Создать заявку на новую дату».

10. Не трогать working UI с большими кнопками.

11. Не менять структуру таблиц.

12. Не писать интеграционные тесты, если они требуют изменения окружения.

После изменений обязательно:

- запустить frontend build;
- запустить API;
- убедиться, что Railway-деплой не сломан;
- проверить вручную сценарии:

A. 1 вода → delivered
B. 2 воды → partial 1
C. 2 воды → failed
D. 2 воды → rescheduled
E. Молоко x5 → partial 2

В ответе покажи только:
- где был настоящий баг;
- как теперь определяется quantity;
- почему partial больше не должен ломаться;
- какие файлы были изменены.
