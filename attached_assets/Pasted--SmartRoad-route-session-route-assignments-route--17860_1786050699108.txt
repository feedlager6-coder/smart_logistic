Ознакомься с архитектурой SmartRoad и текущей реализацией route_session / route_assignments / route_executions.

Нужно не просто исправить баг, а ОКОНЧАТЕЛЬНО привести логику количества товаров и частичной доставки к правильной бизнес-модели.

Контекст:
- Проект используется для воды, продуктов, мебели и B2B-доставок.
- Водитель открывает защищённую ссылку без логина.
- Диспетчер видит исполнение по каждой машине.
- Сейчас часть точек имеет quantity = 0, хотя в поле products указано количество (например: «2 воды», «1 вода», «Воды 3» и т.д.).
- Из-за этого partial даёт HTTP 422.

Сначала проанализируй:
1. Откуда сейчас берётся quantity при создании route_executions.
2. Как формируется поле products.
3. Почему у первой точки quantity есть, а у остальных становится 0.
4. Где quantity теряется: импорт, маршрутизация, сохранение execution или сериализация.

После анализа реализуй ПРАВИЛЬНУЮ модель.

ТРЕБОВАНИЯ

1. Плановое количество
Для каждой точки должно существовать отдельное числовое поле plan_qty.

Если источник уже передал quantity — использовать его.
Если quantity отсутствует, попытаться восстановить из products.

Поддержать типичные записи:
- «2 воды»
- «1 вода»
- «Воды 3»
- «Вода 19л x2»
- «2 бутыли»
- «Бутыль 1»
- «Молоко x5»

Используй надёжный парсер, а не один regex на удачу.

Если количество определить невозможно — использовать 1, а не 0.

Никогда не создавать execution с plan_qty = 0.

2. Фактическое количество
actual_qty хранится отдельно.

Правила:
- delivered: actual_qty == plan_qty
- partial: 0 < actual_qty < plan_qty
- failed: actual_qty = 0
- rescheduled: actual_qty = 0

3. Остаток
Вычислять:
remaining_qty = plan_qty - actual_qty

Показывать у водителя и диспетчера.

Пример:
План 2
Доставлено 1
Остаток 1

4. Частичная доставка
Исправить 422 окончательно.

Сценарий:
- products = «2 воды»
- status = partial
- actual_qty = 1
- payment_method = cash
- payment_status = paid

Должен успешно сохраняться.

5. Создание остатка
Для partial диспетчер должен видеть кнопку:
«Создать заявку на остаток».

Новая заявка создаётся только на remaining_qty.

6. Не доставлено
Для failed диспетчер должен видеть:
«Создать заявку на новую дату».

Создаётся заявка на весь plan_qty.

7. Перенесено
Сохранить текущую рабочую логику переноса.
Но убедиться, что переносится именно недоставленный объём.

8. UI
У водителя показывать:
- План
- Доставлено
- Остаток

У диспетчера:
- План
- Доставлено
- Остаток
- Оплата
- Комментарий

9. Важное архитектурное ограничение
Не меняй алгоритм маршрутизации.
Не добавляй GPS, ETA, WebSocket и новые крупные сущности.
Исправления должны быть совместимы со старыми route_sessions.

10. Обратная совместимость
Для уже существующих execution с quantity=0:
- попытаться восстановить количество из products автоматически при чтении или миграции.

11. Тесты (обязательно)
Проверь сценарии:

A. products=«1 вода» → delivered 1
B. products=«2 воды» → partial 1
C. products=«2 воды» → failed
D. products=«2 воды» → rescheduled
E. products=«Молоко x5» → partial 2
F. products=«Сыр» → delivered 1

В конце дай отчёт:
- где была настоящая причина бага,
- как теперь определяется plan_qty,
- какие форматы товаров поддерживаются,
- какие данные мигрированы,
- почему partial больше не должен ломаться.
