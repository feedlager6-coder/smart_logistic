SMARTROUTE — ПОЛНЫЙ АУДИТ, ДОРАБОТКА И СРАВНЕНИЕ С ЯНДЕКС

Перед любыми изменениями изучи проект полностью:

1. Прочитай весь код маршрутизации.
2. Изучи текущую архитектуру построения маршрутов.
3. Изучи все предыдущие изменения, которые уже были внесены.
4. Проверь, какие выводы из предыдущих расследований действительно подтверждаются кодом и реальными данными.
5. Изучи структуру Railway PostgreSQL.
6. Изучи реальные маршруты из route_sessions и route_session_stores.
7. Не доверяй предыдущим отчётам автоматически. Всё перепроверь самостоятельно.

После полного погружения в проект выполни расследование.

Контекст проблемы:

* В системе 120 магазинов и 9 автомобилей.
* Один маршрут регулярно получает 33-37 точек.
* Яндекс после нажатия “Оптимизировать маршрут” улучшает маршрут примерно на 14 минут.
* В некоторых сценариях SmartRoute строит лучше Яндекса, но чаще Яндекс выигрывает.
* Основная цель: понять реальные причины отставания и устранить их.

Требования к расследованию:

1. Используй реальные данные Railway PostgreSQL.
2. Используй реальные route_sessions.
3. Используй реальные route_session_stores.
4. Не делай предположений без измерений.
5. Для каждого вывода показывай цифры и доказательства.

Особенно проверь:

* распределение магазинов между автомобилями;
* причины появления маршрутов на 33-37 точек;
* работу sweep-кластеризации;
* работу centroid refinement;
* работу OR-Tools;
* работу two-opt;
* работу inter_route_relocate;
* работу rebalance_min_stops;
* использование Haversine;
* использование OSRM;
* использование GraphHopper;
* корректность ETA.

Проверь предыдущие гипотезы:

1. Недостаточный time limit OR-Tools на больших маршрутах.
2. Использование Haversine в relocate вместо реальных дорог.
3. Некорректный ETA.
4. Перегрузка отдельных кластеров.
5. Влияние дублирующихся координат.
6. Любые другие причины деградации качества маршрутов.

Разрешённые изменения (внедрять сразу):

1. Адаптивное увеличение времени OR-Tools для крупных кластеров.
2. Исправление расчёта ETA на основе реальных дорог.
3. Любые улучшения, которые подтверждены цифрами и имеют низкий риск.

Запрещено без доказательств:

* менять алгоритм кластеризации;
* менять sweep на balanced sweep;
* внедрять новые способы распределения между машинами;
* ограничивать размеры кластеров;
* менять логику маршрутизации без измеримого подтверждения пользы.

После внедрения безопасных улучшений:

Проведи стресс-тесты:

50 точек
120 точек
200 точек
300 точек

Для каждого сценария покажи:

* total km;
* время расчёта;
* max/min stops;
* количество точек по каждому автомобилю;
* качество маршрутов;
* любые деградации.

После этого проведи сравнение SmartRoute и Яндекс.

Если потребуется сравнение с Яндекс:

Я предоставлю:

1. Маршрут SmartRoute.
2. Тот же маршрут после оптимизации Яндексом.

Тогда необходимо:

* сравнить порядок посещения точек;
* найти конкретные перестановки;
* определить какие эвристики использовал Яндекс;
* показать где SmartRoute теряет время;
* предложить способы получить такой же результат без использования API Яндекса.

Главная цель:

Сделать так, чтобы SmartRoute стабильно строил маршруты не хуже Яндекса на больших наборах точек, сохранив стабильность системы и не ломая существующую архитектуру.

Ничего не внедряй без измерений.
Все выводы подтверждай цифрами.
Сначала исследование, потом изменения, потом стресс-тест, потом финальный отчёт.
