покрытия дорог Махачкалы (Дагестан). Часть координат не снапится на дорогу → маршрут через
отдалённые точки → road_factor 32–117×. Это само по себе контраргумент против OSRM.

#### Анализ валидных сценариев (rf < 5×, n=7)

| Метрика | Значение |
|---------|---------|
| Среднее Δpct (OSRM − Hav) | **−6.4%** (ниже порога 15%) |
| Медиана Δpct | −7% |
| Средний saved_km ratio | **1.308×** (наш ROAD_FACTOR = 1.4) |
| road_factor opt (avg) | 1.728× |
| road_factor base (avg) | 1.475× |
| OSRM overhead времени | **+19%** (ниже порога 20%) |

#### Решение

| Критерий | Порог | Факт | Итог |
|---------|-------|------|------|
| Δsaved_pct ≥ 15% | 15% | 6.4% | ❌ НЕ ВЫПОЛНЕН |
| overhead ≤ 20% | 20% | 19% | ✅ ВЫПОЛНЕН |
| Надёжность OSRM | 0% аномалий | 30% аномалий | ❌ НЕПРИЕМЛЕМО |

**Вывод: ❌ НЕ ПЕРЕХОДИТЬ НА OSRM. Текущая модель Haversine + ROAD_FACTOR=1.4 остаётся.**

Обоснование:
1. saved_pct меняется лишь на −6.4% — это говорит о том, что road_factor для
   optimized (1.728×) и baseline (1.475×) близки, и Haversine корректно измеряет
   ОТНОСИТЕЛЬНУЮ экономию с обеих сторон.
2. Публичный OSRM ненадёжен для российских городов: 30% сценариев вернули мусор.
   В production это означало бы случайное завышение/занижение показателей в 32–117 раз.
3. ROAD_FACTOR=1.4 хорошо аппроксимирует OSRM: средний ratio = 1.308 (ошибка ≤10%).
4. Добавление OSRM Route API создаёт зависимость от внешнего сервиса, который и сейчас
   используется только для оптимизации порядка, но не для отчётности.

## [Unreleased] — 2026-05-31 (OSRM Integration + Stress Tests)

### Новая функция `get_cluster_matrix_osrm(coords)`

Добавлен второй слой в цепочку маршрутизации: **GH → OSRM → Haversine**.

- OSRM использует реальные дороги OpenStreetMap (односторонние улицы, мосты, объезды)
- Публичный сервер `router.project-osrm.org`: бесплатный, без API-ключа, до 100 точек
- Конфигурируется через `OSRM_BASE_URL` (для self-hosted инсталляции) и `OSRM_MAX_LOCATIONS`
- Координаты в OSRM URL передаются в порядке **lon,lat** (не lat,lon!)
- Кэш: единый `_matrix_cache` с префиксом `("osrm",)` во избежание коллизий с GH
- Rate-limit TTL: 30 сек при HTTP 429/503 или таймауте ≥ 14 сек
- Счётчики: `_osrm_call_successes`, `_osrm_cache_hits`

### Изменения в `solve_vrp()` Step 3

До: GH → Haversine
После: **GH → OSRM → Haversine** (приоритет по каждому кластеру независимо)

Обновлены счётчики: `gh_clusters`, `osrm_clusters`, `hv_clusters` (был только `gh`/`hv`).
Обновлён `matrix_source`: добавлено значение `"osrm"` и корректный `"mixed (gh=N, osrm=M, hv=K)"`.

### Startup logging

Теперь при запуске логируется полная цепочка:

## [Unreleased] — 2026-05-31 (GraphHopper Per-Cluster Matrices)

### Архитектура

Реализована гибридная схема: **A → кластеризация → B → GH матрица per-cluster → C → OR-Tools TSP**.

Ранее GraphHopper использовался только для датасетов ≤ 5 точек (весь маршрут одним запросом).
Теперь — для каждого кластера отдельно, после равно-угловой секторной разбивки.

### Новая функция `get_cluster_matrix_gh(coords)`

Заменила прямой вызов `get_matrix_from_graphhopper` внутри `solve_vrp`.

- Принимает до `GRAPHHOPPER_CLUSTER_MAX` точек (default 25, Free план = 5)
- **In-memory кэш**: `_matrix_cache[tuple(sorted_coords)] → (dist_matrix, time_matrix)`.
  Повторный вызов с теми же точками: 0 API запросов, мгновенно.
- **Раздельные счётчики**: `_matrix_cache_hits`, `_matrix_cache_misses`, `_gh_call_successes`
- **Авто-калибровка плана**: при 400 "Too many points, allowed: N" — автоматически снижает
  `_gh_plan_limit` до N. Все последующие кластеры > N пропускаются без API-запроса.
- Логирование каждого вызова: latency ms, размер матрицы, счётчики кэша

### Изменения в `solve_vrp()` Step 3

До: `sub_matrix = haversine_submatrix(cluster)` → всегда
После: `get_cluster_matrix_gh(depot + cluster)` → fallback `haversine_submatrix` если GH недоступен

Лог после каждого `solve_vrp`:
```
solve_vrp clusters: total=4, graphhopper=2, haversine=2, elapsed=1.2s, cache_hits=0, cache_total=2
```

### Исправлен баг в `_cluster_by_sweep`

`max_stops_per_cluster` (undefined variable) → `max_cluster_size` (правильный параметр)

### Добавлено

- `_gh_plan_limit: int` — авто-детектированный лимит плана GH (старт = GRAPHHOPPER_CLUSTER_MAX)
- `_gh_call_successes: int` — счётчик успешных GH API вызовов
- `scripts/test_vrp_graphhopper.py` — сравнительный тест Haversine vs GH с тремя сценариями

### Статус GH ключа в проекте

**Free план**: max 5 точек/матрица. Все реальные кластеры (6–25 точек) превышают лимит.
Авто-детекция автоматически снижает `_gh_plan_limit` → 5 после первого 400 ответа.
Все маршруты строятся через Haversine fallback. **Маршруты оптимальны географически.**

**При апгрейде**: установить `GRAPHHOPPER_CLUSTER_MAX=25` (или выше) в env — GH начнёт
применяться для каждого кластера, OR-Tools получит реальные дорожные расстояния.

## [Unreleased] — 2026-05-31 (VRP Efficiency-First Routing)

### Причина изменений

Обнаружена критическая проблема: система распределяла магазины между водителями принудительно равномерно (8-8-8-9), игнорируя географию. Цель системы — минимальный пробег, а не справедливость. Исправлено.

### Что было причиной равномерного распределения

Два независимых источника принудительного выравнивания:

1. **`SetGlobalSpanCostCoefficient(100)`** в `_ortools_full()` — прямой штраф OR-Tools за разницу между длиннейшим и кратчайшим маршрутом. Убран полностью.
2. **Round-robin кластеризация** в `_cluster_by_sweep()` — магазины раздавались по принципу "каждому по очереди" (`i % num_vehicles`), как карты в колоде. Заменена на равно-угловые секторы.

### Что изменено

**`artifacts/api-server/main.py`** — единственный изменённый файл:

- **`_cluster_by_sweep()`**: round-robin → равно-угловые секторы (360° / N машин).
  Плотные секторы получают больше точек, разреженные — меньше. Добавлен параметр `max_cluster_size`.
- **`solve_vrp()`**: полностью переработана архитектура (убраны Tier 1/2/3):
  - Строится полная NxN матрица Haversine один раз (мгновенно, без API)
  - Для малых датасетов (≤ GH_FREE_LIMIT) сначала пробуется GraphHopper
  - Секторная разбивка → OR-Tools TSP на каждый сектор
  - Новый Шаг 4: если угловой сектор оказался пуст, крупнейший маршрут разбивается пополам по углу
- **`_ortools_solve_group()`**: time limit уменьшен до 2 секунд (было 5)
- Убран `SetGlobalSpanCostCoefficient` — нет балансировочного штрафа

### Алгоритм после изменений

```
1. Haversine NxN матрица (или GraphHopper для малых наборов)
2. Равно-угловые секторы от депо → каждая машина получает "клин"
   Плотный клин → больше точек. Пустой клин → нет точек (обрабатывается на шаге 4)
3. OR-Tools TSP на каждом секторе → оптимальный порядок объезда
4. Если маршрутов < машин → разбить крупнейший по угловому центроиду
```

### Результаты тестов

| Сценарий | До (наивный baseline) | После | Экономия |
|---|---|---|---|
| 33 магазина / 4 машины | 81.69 км | 25.71 км | **−68.5%** |
| 52 магазина / 6 машин | 180.54 км | 52.03 км | **−71.2%** |
| 12 плотных вост. + 12 разбросанных / 4 машины | 90.92 км | 34.48 км | **−62.1%** |

Распределение сценария А: **[12, 12, 7, 2]** вместо [9, 8, 8, 8] — теперь 2 машины отрабатывают плотные кластеры, 1 — восточные выезды, 1 — одиночки.
